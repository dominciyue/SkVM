## Executive Conclusion

### Source behavior — raw conclusion

The reviewed source appears to allow an authenticated principal with **read permission to the repository’s issues unit, but without write permission**, to create a basic issue.

The route requires an authenticated token, an unarchived and accessible repository, valid request binding, and `reqRepoReader(unit.TypeIssues)`. It does **not** use an issues-unit writer guard. Within `CreateIssue`, the explicit `CanWrite(unit.TypeIssues)` checks restrict issue metadata, but the non-writer branch still calls `issue_service.NewIssue`.

A principal with issues-unit write permission can also create an issue and can additionally provide the metadata reserved to writers.

### Independent policy assessment

**Raw source-based assessment: VIOLATED.**

The route admits issues-unit readers, and the source-visible non-writer branch still reaches issue insertion. Thus the behavior visible in this revision conflicts with the policy.

### Risk

An authenticated reader may be able to modify repository state by creating issues despite lacking write permission to the issues unit. Under the supplied policy, this is an authorization boundary violation: repository read permission alone must not authorize the write.

### Relevant failure and post-effect exceptions

Creation is not unconditional. It can be prevented by, among other things:

- Missing or unacceptable authentication/token;
- Repository lookup or visibility failure;
- Token inability to access the repository;
- Applicable token-scope restrictions;
- Enforced two-factor authentication producing no repository access;
- An archived repository;
- Request-binding or metadata-validation errors;
- Blocked-user relationships;
- Assignee resolution or assignability failure on the writer path;
- Database or other operational errors.

There is also an important post-effect distinction: if the request asks for the issue to be initially closed, `CloseIssue` runs after `NewIssue`. Refetch or close processing can fail after creation. An API error response therefore does not necessarily establish that no issue was inserted.

### Recommended remediation

Require issues-unit write permission before invoking the creation service—for example, by applying the repository writer middleware for `unit.TypeIssues` at the POST route or by returning a denial from `CreateIssue` when:

```go
!ctx.Repo.Permission.CanWrite(unit.TypeIssues)
```

The check should protect the creation operation itself rather than only optional metadata.
