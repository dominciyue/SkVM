### Command / Code Injection

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
🟠 HIGH — Tag-controlled value interpolated into JavaScript source
Confidence: HIGH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

📍 Locations:
- `source/release.yml`, lines 52–57 (`build` job)
- `source/release.yml`, lines 127–131 (`npm-publish` job)

🔍 Vulnerable Code:
```yaml
node -e "
  const fs = require('fs');
  const p = JSON.parse(fs.readFileSync('package.json','utf8'));
  p.version = '${{ steps.version.outputs.version }}';
  fs.writeFileSync('package.json', JSON.stringify(p, null, 2) + '\\n');
"
```

The value ultimately comes from the pushed tag:
```sh
tag="${GITHUB_REF#refs/tags/}"
version="${tag#v}"
```

⚠️ Risk:

The tag-derived version is inserted into a single-quoted JavaScript string before `node -e` executes. Git tag names are controlled by whoever can create or push tags matching `v*`; the workflow does not validate the value as a safe version before inserting it into source code. A crafted tag containing a quote and JavaScript expression could escape the string and execute code on the runner.

The resulting code would run in the `build` job and, independently, the same pattern exists in the `npm-publish` job. The build job inherits workflow-level `contents: write` and `id-token: write`; the publish job can mint an OIDC token and publish to npm when its condition allows it. Actual exploitability depends on who can create tags and on repository/npm trust configuration, which were not verified offline.

✅ Recommended Fix:

Pass the value through the step environment and read it from `process.env`; do not interpolate it into JavaScript source. Also validate the tag/version against the intended semver policy before publishing.

Example fixed pattern for the build job:
```yaml
- name: Sync package.json version to tag
  env:
    PACKAGE_VERSION: ${{ steps.version.outputs.version }}
  run: |
    node -e '
      const fs = require("fs");
      const p = JSON.parse(fs.readFileSync("package.json", "utf8"));
      // Read untrusted tag data as data, not as JavaScript source.
      p.version = process.env.PACKAGE_VERSION;
      fs.writeFileSync("package.json", JSON.stringify(p, null, 2) + "\\n");
    '
```

Apply the same environment-variable pattern to the `npm-publish` job. Add an explicit allowlist/semver validation step before either synchronization or publishing.

📚 Reference: OWASP A03:2021 – Injection; GitHub Actions script-injection guidance

### Authentication / Authorization and Workflow Token Permissions

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
🟡 MEDIUM — Workflow-wide write permissions inherited by unrelated jobs
Confidence: HIGH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

📍 Location: `source/release.yml`, lines 8–10; job permission state at `workflow-inventory.json`

🔍 Evidence:
```yaml
permissions:
  contents: write
  id-token: write
```

The inventory records:
- `build`, line 13: job permissions **omitted** — inherits the workflow declaration.
- `release`, line 71: job permissions **omitted** — inherits the workflow declaration.
- `npm-publish`, line 96: explicitly declares `contents: read` and `id-token: write`.

⚠️ Risk:

Because `build` and `release` omit job-level permissions, they inherit both workflow-level write permissions. The build steps appear to compile and upload artifacts and do not obviously require repository write access or OIDC token issuance. The release job needs repository contents write access for release creation, but does not obviously need `id-token: write`. If an action, dependency installation step, or injected command is compromised, inherited permissions increase the possible impact.

✅ Recommended Fix:

Declare least-privilege permissions per job. For example, use `permissions: {}` for `build` if artifact upload works under the repository's required artifact permission model, use only `contents: write` for `release`, and retain only `contents: read` plus `id-token: write` for `npm-publish`. Confirm required artifact permissions in a controlled review before applying.

This finding is a permissions design issue, not proof that the workflow is exploitable in the repository's live configuration.
