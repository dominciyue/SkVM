## Executive Conclusion

An authenticated principal who passes the API route’s **issues-unit read** check can create a basic issue even when:

```go
ctx.Repo.Permission.CanWrite(unit.TypeIssues)
```

is false.

The route does not require issues-unit write permission. Inside `CreateIssue`, write permission only determines whether the caller may supply privileged metadata such as deadline, milestone, labels, assignees, and projects. The non-writer branch removes or ignores those fields but still calls `issue_service.NewIssue`.

Therefore:

| Principal condition | Source behavior | Independent policy |
|---|---|---|
| Issues-unit write permission | Can create, including privileged metadata | Allow |
| Issues-unit read but not write | Can create a basic issue | Deny |
| Repository/site administrator admitted by reader middleware | Can reach creation path; effective write status determines metadata | Policy still requires issues-unit write |
| Unauthenticated | Rejected by token middleware | Deny |
| Archived repository | Rejected before handler | Deny |

The successful reader-without-write path is a direct policy violation.

### Route-level controls

The issue route is protected by authentication, archived-repository rejection, and an issues-unit reader check. The relevant middleware is `reqRepoReader(unit.TypeIssues)`, not an issues-unit writer requirement.

`reqRepoReader` admits a caller when the resolved repository permission can **read** the requested unit. Repository administrators and site administrators are relevant exceptions to the ordinary reader test.

Consequently, this is narrower than “any person who can read any part of the repository”: the caller must pass the route’s issues-unit reader/admin control. But it is still weaker than the independent policy’s required issues-unit write permission.

### Creation effect

The reviewed `issue_service.NewIssue` path:

1. Loads the poster.
2. Checks whether the poster is blocked by the repository owner or requested assignees.
3. Opens a transaction.
4. Calls the model issue-creation operation.
5. Processes assignees and projects.
6. Processes mentions and notifications.

No issues-unit write-permission check was visible in that reviewed service function before the model creation call.

The protected effect is therefore performed for the repository selected by the route and for the authenticated caller supplied as `ctx.Doer`, provided the reader/admin route controls and operational checks succeed.

### Risk

Against the independently supplied policy, an authenticated principal with issues-unit read access but without issues-unit write access can perform a write operation: creating an issue.

The caller cannot use this path to set all writer-only metadata, but restricting metadata does not satisfy a policy that requires write permission for the creation itself.

### Policy comparison

#### Principal with issues-unit write permission

**Actual behavior:** Allowed to create and may submit writer-only metadata.  
**Required behavior:** Allowed.  
**Result:** Compliant for this principal class.

#### Authenticated issues-unit reader without write permission

**Actual behavior:** Allowed to create a basic issue. Labels are cleared, and deadline, milestone, assignees, and projects are not accepted through the writer branch.  
**Required behavior:** Denied.  
**Result:** **Non-compliant.**

### Relevant exceptions and non-authorization failures

The following conditions can stop or modify the path, but none supplies the missing write authorization:

- **Authentication:** `reqToken` rejects callers who are not signed in.
- **Archived repository:** `mustNotBeArchived` rejects creation before the handler.
- **Repository/site administrators:** `reqRepoReader` contains administrator alternatives to the normal unit-read test. This broadens route admission but is not itself the independent policy’s required issues-unit write check.
- **Blocked users:** the service rejects a poster blocked by the repository owner or a requested assignee.
- **Invalid assignee data:** writer-only assignee validation may terminate the request.
- **Transaction or database error:** creation may fail operationally.
- **Mention processing:** this occurs after transactional creation; a later error may produce an API error even though the issue has already been created.
- **Optional immediate closure:** when `form.Closed` is set, `CloseIssue` runs after creation. An open-dependency or other close error can therefore produce an error response after the issue already exists.
- **Refetch/serialization:** the handler refetches the issue after creation. A refetch failure can also occur after the protected effect.

These later failures are important because an error response does not necessarily mean that issue creation was rolled back.

## Recommended Fix

Enforce the issues-unit write requirement before constructing or creating the issue. This can be done through route middleware or an explicit handler check. The authorization should apply to the creation operation itself, not merely to optional metadata.

### Patch proposal

⚠️ **Review each patch before applying. Nothing has been changed yet.**

**Before:**

```go
func CreateIssue(ctx *context.APIContext) {
    form := web.GetForm[*api.CreateIssueOption](ctx)
    var deadlineUnix timeutil.TimeStamp
    if form.Deadline != nil && ctx.Repo.Permission.CanWrite(unit.TypeIssues) {
        deadlineUnix = timeutil.TimeStamp(form.Deadline.Unix())
    }
```

**After:**

```go
func CreateIssue(ctx *context.APIContext) {
    // Creating an issue is a write to the issues unit.
    if !ctx.Repo.Permission.CanWrite(unit.TypeIssues) {
        ctx.APIError(http.StatusForbidden, "write permission to the issues unit is required")
        return
    }

    form := web.GetForm[*api.CreateIssueOption](ctx)
    var deadlineUnix timeutil.TimeStamp
    if form.Deadline != nil {
        deadlineUnix = timeutil.TimeStamp(form.Deadline.Unix())
    }
```

After adding the mandatory check, the later `CanWrite` branches could be simplified because all continuing callers have already passed the required permission check. Alternatively, replace the route’s reader middleware with an existing, verified issues-unit writer middleware if this revision provides one with the intended administrator and unit-availability semantics.

Tests should cover at least:

1. Authenticated issues reader without write permission → `403`, no issue persisted.
2. Issues writer → issue created.
3. Repository/site administrator → behavior explicitly established according to effective issues-unit permission.
4. Archived repository → still rejected.
5. Failed close or refetch after creation → test whether the API response accurately represents the already-committed effect.
