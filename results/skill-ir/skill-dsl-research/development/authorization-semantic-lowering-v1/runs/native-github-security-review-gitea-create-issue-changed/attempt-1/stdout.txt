### Actual source behavior

The API route is registered with token authentication and repository-level controls, including the issue-unit reader gate. The observed route path applies `reqRepoReader(unit.TypeIssues)` before dispatching to `CreateIssue` (`routers/api/v1/api.go:1638–1740`).

Inside `CreateIssue`:

- The selected repository is `ctx.Repo.Repository`.
- The authenticated caller is bound to the issue through `ctx.Doer.ID` and `ctx.Doer`.
- The handler invokes `issue_service.NewIssue(...)` at `routers/api/v1/repo/issue.go:624`.
- The handler does **not** require `ctx.Repo.Permission.CanWrite(unit.TypeIssues)` before creating the issue.

The `CanWrite(unit.TypeIssues)` checks in `CreateIssue` are conditional handling checks:

```go
if form.Deadline != nil && ctx.Repo.Permission.CanWrite(unit.TypeIssues) {
    ...
}
```

and:

```go
if ctx.Repo.Permission.CanWrite(unit.TypeIssues) {
    issue.MilestoneID = form.Milestone
    ...
} else {
    form.Labels = make([]int64, 0)
}
```

These checks control optional fields such as deadlines, milestones, assignees, and labels. They are not the entry authorization for issue creation. `CanWrite` itself means write access to the specified unit (`models/perm/access/repo_permission.go:152–155`).

The creation service then loads the poster, checks blocked-user relationships, and persists the issue inside a transaction:

```go
if err := issues_model.NewIssue(ctx, repo, issue, labelIDs, uuids); err != nil {
    return err
}
```

(`services/issue/issue.go:25–84`). The shown `NewIssue` path contains no issue-unit `CanWrite` check.

## Relevant exceptions

These exceptions affect whether a particular request succeeds, but they are not equivalent to requiring issue-unit write permission:

1. **Archived repository**  
   The route applies an archived-repository rejection control before creation. The available route evidence identifies `mustNotBeArchived` as part of the route controls.

2. **Blocked poster**  
   `NewIssue` rejects creation when the poster is blocked by the repository owner or an assignee (`services/issue/issue.go:30–32`).

3. **Invalid optional metadata**  
   Assignee lookup, assignability checks, project handling, and related validation can fail. These are input or secondary-operation failures, not a general issue-unit write gate.

4. **Creating an initially closed issue**  
   If `form.Closed` is requested, the handler invokes `issue_service.CloseIssue` after creation (`routers/api/v1/repo/issue.go:635–644`). That introduces additional close/dependency behavior. The source-visible conclusion for ordinary open issue creation should not automatically be extended to every closed-issue variant.

5. **Persistence or refetch failures**  
   Database errors, notification-related failures, or the final issue refetch can prevent a successful `201` response even after the creation path has begun.
