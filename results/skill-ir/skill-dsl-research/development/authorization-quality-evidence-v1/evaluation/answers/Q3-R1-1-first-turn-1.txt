### Effective version selection

Version selection happens only after root authorization succeeds.

| Request condition | Effective file document |
|---|---|
| `pk` names a version and `version` is absent | That exact requested version, including a deleted version found by the initial global lookup |
| `version` absent and the requested row is a root | Newest row from `Document.objects` related to the root, or the root if none |
| `version=` is present but empty | Newest related row using `global_objects`, or the root |
| `version=<truthy integer>` | That ID, only if it is the root itself or has `root_document_id == authorized_root.id` |
| Truthy non-integer version | 404 (`NotFound("Invalid version parameter")`) |
| Missing or unrelated version ID | 404 |

“Newest” means `version_index` descending with nulls last, then `id` descending.

## 2. Authorization checks and selection order

The source order is:

1. **DRF admission before the action.** `APIView.initial()` performs authentication, global permissions, and throttling before invoking the handler.  
   `framework/rest_framework-3.18.1/rest_framework/views.py:404-421`

2. **Configured global permissions.** `DocumentViewSet` uses:
   - `IsAuthenticated`
   - `PaperlessObjectPermissions`  
   `src/documents/views.py:1008-1022`

3. **GET model permission.** `PaperlessObjectPermissions` maps GET to `documents.view_document`; inherited `has_permission()` checks `request.user.has_perms(...)`.  
   `src/documents/permissions.py:30-44`  
   `framework/rest_framework-3.18.1/rest_framework/permissions.py:233-246`

4. **Requested-row and root lookup.** The action looks up `pk`, then derives the root as described above.

5. **Custom root-object check.** When `request.user is not None`, `has_perms_owner_aware(user, "view_document", root_doc)` allows:
   - an unowned root;
   - a root owned by the requester; or
   - an otherwise owned root for which Guardian’s `ObjectPermissionChecker.has_perm()` returns truthy.

   Failure returns an explicit 403. The checker is constructed before the owner-or-grant expression is evaluated; only `has_perm` is short-circuited by unowned/self-owned roots.

   `src/documents/views.py:1421-1427`  
   `src/documents/permissions.py:624-635`

6. **Version and representation selection.** Only after the root check passes does the code select `file_doc`, decide archive/original, and call `serve_file`.  
   `src/documents/views.py:1429-1448`

The action does not call `get_object()` or `check_object_permissions()` for either the requested row or selected `file_doc`. Consequently, `PaperlessObjectPermissions.has_object_permission()` is not invoked on the selected version in this path; the operative object-level decision is the explicit root check.

The `request.user is None` branch skips the custom root check, but under normal dispatch it should be unreachable unless the preceding authentication/permission behavior is altered or bypassed. The supplied evidence does not establish such a condition.

## 3. Does alternate selection change the authorized resource?

Generally, **no**:

- Authorization is evaluated first against the resolved root document.
- Selecting the root, latest version, a specific related version, or the exact version named by `pk` can change `file_doc`, but does not replace the already-authorized root.
- There is no owner-aware or inherited DRF object-permission recheck on `file_doc`.
- `original` versus archive changes only the file handle, filename/MIME behavior, and returned representation; it does not change the authorization target.

`src/documents/views.py:1421-1448`

The important exceptional root-resolution branch is structural: if a requested version references a root that cannot be loaded, `get_root_document()` falls back to the requested version itself. In that case the requested version becomes the object checked as the “root.” This happens during root resolution, not because later version or archive selection changes the authorization target.

An explicit version must still belong to the authorized root—or be the root itself—or selection ends in 404. That is a relationship constraint, not an additional authorization check.
