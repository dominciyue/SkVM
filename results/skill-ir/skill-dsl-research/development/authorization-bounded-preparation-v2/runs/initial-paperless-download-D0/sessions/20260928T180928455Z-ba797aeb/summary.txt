Conclusions
- scenario%3Aversion-owner-no-root-view::entry%3Adownload: source_refuted — At the declared DocumentViewSet.download entry, the handler delegates to file_response. Before selecting or serving any file, the source resolves the requested document and its root, then applies has_perms_owner_aware to the root document for view_document. That check permits ownership of the checked object, an unowned object, or an explicit object permission; ownership of the requested version does not satisfy a check on a differently owned root. Under the supplied premise that the caller lacks a root view grant and the root is owned by someone else, the root check returns false and file_response returns HttpResponseForbidden, so the protected file-serving effect is not reached. The file object that would otherwise be served is selected only after that check by _get_effective_file_doc: for a version request, it can be the requested version document, and serve_file would receive that selected file_doc. Thus the source-visible behavior is deny, consistent with the accepted root-view policy. No decisive source-external runtime fact is required within the declared boundary; this is not a repository-wide or deployment-completeness claim.
