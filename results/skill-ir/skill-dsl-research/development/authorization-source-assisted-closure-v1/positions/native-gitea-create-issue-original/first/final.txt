## Executive Conclusion

**Raw source conclusion:** The examined API path appears **noncompliant** with the independently supplied policy.

> **Independent CURRENT policy:** “Creating an issue requires write permission to the repository's issues unit. Read permission to the repository alone does not authorize this write.”

The route requires authentication but admits a principal with **read** access to the issues unit. Within `CreateIssue`, issues-unit write permission controls privileged optional fields such as deadline, milestone, assignees, and labels, but the basic `issue_service.NewIssue(...)` call remains on the path for a non-writer. Subject to validation and service-layer failure conditions, an authenticated issues-unit reader can therefore reach the issue-creation effect.

This is a source-conformance conclusion for the cited revision—not confirmation of behavior in a particular deployment.

### Risk

Against the supplied policy, a principal possessing only issues-unit read permission can perform a write operation: creating a basic issue. The writer/non-writer distinction changes optional issue metadata, but does not visibly change whether the issue itself can be created.

This is a broken authorization-policy boundary in deployments where the independently supplied policy is authoritative.

### Relevant exceptions and non-authorizing controls

These conditions can prevent a particular request from succeeding, but do not implement the policy’s required issues-unit-write predicate:

1. **Authentication:** `reqToken` requires `ctx.IsSigned`.
2. **Repository archive status:** archived repositories are rejected.
3. **Repository/site administrators:** expressly bypass the route’s ordinary reader test.
4. **Blocked-user relations:** the service rejects a poster blocked by the repository owner, and shown assignee-related block conditions.
5. **Request binding and validation:** malformed form data or invalid optional objects may fail.
6. **Assignee eligibility:** optional assignment has its own permission rules. For example, `CanBeAssigned` accepts any write access or pull-request read access, but this governs assignment—not basic issue creation:

### Independent policy assessment

**Status: VIOLATED — raw source conclusion**

The supplied policy requires issues-unit write permission and explicitly states that read permission alone is insufficient. The visible route admits issues-unit readers, and the visible handler allows the creation call to remain after its non-writer branch.

The repository-administrator and site-administrator paths need separate policy interpretation: the supplied policy does not explicitly say whether those roles inherently count as possessing effective issues-unit write permission. That ambiguity does not remove the ordinary authenticated read-only path.

### Recommended fix

Require effective write permission to `unit.TypeIssues` before issue construction or before calling `issue_service.NewIssue`. Keep the writer-only metadata branches only if they serve additional validation purposes; they must not substitute for the operation-level guard.

- **Administrative inheritance:** Repository/site admin handling is an exception requiring separate interpretation and is not used to prove the ordinary reader path.

Because the deeper semantic closure and final domain check failed, the finding remains **Medium confidence** despite strong direct route/handler evidence.
