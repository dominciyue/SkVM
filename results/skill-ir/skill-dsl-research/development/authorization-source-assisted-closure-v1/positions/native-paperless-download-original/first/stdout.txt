## 3. Does choosing another version change the authorized resource?

### Version-family selection

The version resolver accepts an explicit version identifier only if:

- it parses as an integer;
- the candidate exists;
- the candidate is the requested root document itself, or its `root_document_id` points to that root.

[src/documents/versioning.py:169–195, `ev-102f8b0754d25f90f094`; manager selection at lines 136–137, `ev-502c2ef27e090c2a8bdc`]

An invalid, missing, malformed, or unrelated version is rejected by the resolver. Without an explicit version parameter, the resolver selects the latest version for the root. The version ordering uses `version_index` descending, followed by descending id. [src/documents/versioning.py:23–28, `ev-0a3e2110490f204c7a6a`; `ev-102f8b0754d25f90f094`]

### Effective file document

The visible `_get_effective_file_doc` branch is:

- if `request_doc` is already a version and no version parameter is present, return `request_doc`;
- otherwise resolve a file document from `root_doc` and the request.

[src/documents/views.py:1388–1399, `ev-b55350fecebab52a88d2`]

Thus, based on the source examined:

- the requested `pk` identifies the initial `request_doc`;
- `root_doc` is the object used by the visible authorization check;
- a selected version can become the effective file document;
- the effective file document is the object whose stored file or archive representation is passed to file serving.

### Security implication

Selecting another permitted version appears to change **the file resource returned within the same root-document family**, while the visible authorization decision remains attached to `root_doc`.

The examined source does **not** show a second owner/grant authorization check on the selected version immediately before serving it. However, this is not a confirmed vulnerability because:

- permission-class applicability to the Download action was not fully established;
- no runtime fixture was executed.
