- scenario%3Aversion-owner-no-root-view::entry%3Adownload: source_refuted — The download action delegates to file_response. That path binds the authenticated principal from request.user, loads the document named by pk as request_doc, resolves its root as root_doc, and applies the owner-aware view_document check to root_doc—not to the requested version. Under the stated premises, the root is owned by another user and the caller has no object view grant on it, so has_perms_owner_aware returns false and the path returns an insufficient-permissions response before file selection or serving. Ownership of request_doc therefore does not authorize access to root_doc. If authorization passed, the served object would be the effective file document: for a version request_doc with no version query parameter, request_doc itself; otherwise the document selected by version resolution for the root. serve_file then serves that selected document's archive or source file. This source-visible behavior satisfies the accepted requirement that root-document view authorization precede serving any selected version. The assumed global permission and document existence do not alter the decisive root object check.
