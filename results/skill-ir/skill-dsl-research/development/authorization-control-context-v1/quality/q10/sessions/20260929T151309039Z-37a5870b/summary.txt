Conclusions
- scenario%3Aversion-owner-no-root-view::entry%3Adownload: source_refuted — At the declared download entry, the handler delegates to file_response. That path loads the document identified by pk as request_doc, derives root_doc from it, and applies has_perms_owner_aware(request.user, "view_document", root_doc). Thus the protected object is the root document, not the requested version. The owner-aware check succeeds only if the checked root is unowned, is owned by the caller, or the object permission checker grants the requested permission. Under the stated premises, the existing root is owned by a different user and the caller has no object view grant on it, so the check returns false and file_response returns an insufficient-permissions response before selecting or serving a file. The caller's ownership of the requested version does not satisfy authorization on the separately bound root, and the premise that the caller has the global document-view permission does not replace this explicit root-object check. If authorization did proceed, the served doc would be file_doc: for a request_doc that is itself a version and with no separate version query parameter, that is request_doc; otherwise it is the document returned by resolution against root_doc. serve_file then serves that selected doc's archive file when requested and available, or its source file otherwise. Therefore the source-visible behavior for the stated scenario is denial, which conforms to the accepted policy requiring the owner-aware view_document check on the root before any selected version is served.
