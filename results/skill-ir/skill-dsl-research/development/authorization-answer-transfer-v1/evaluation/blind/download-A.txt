## 1. Requested document and returned file

### Entry and initial lookup

- The router registers `UnifiedSearchViewSet` under `documents`; that class inherits `DocumentViewSet`, which supplies `download` (`src/paperless/urls.py:74-77`, `src/documents/views.py:2503`).
- The router-generated relative operation is a GET detail action equivalent to `documents/{pk}/download/`. It calls `file_response(pk, request, "attachment")` (`src/documents/views.py:1834-1839`).
- `file_response` resolves `pk` using `Document.global_objects`, because it passes `include_deleted=True`. Thus even a deleted document can be the initially requested row. A missing `pk` produces 404 (`src/documents/views.py:1401-1415`, `1429-1434`).

### Root resolution

The authorization root is resolved before selecting the file-bearing version:

1. If the requested row has no `root_document_id`, it is the root.
2. Otherwise, use its loaded `root_document`.
3. If unavailable, look up that ID using the selected manager—here the global manager.
4. If that lookup also fails, fall back to the requested row itself.

See `src/documents/versioning.py:146-156`.

### Version selection branches

After root authorization succeeds, `_get_effective_file_doc` selects the document whose file will be served (`src/documents/views.py:1375-1399`, `1437-1445`):

| Request condition | Selected document |
|---|---|
| `pk` names a version and `version` is absent | That exact requested version |
| Root `pk`, `version` absent | Latest non-deleted related version, or root if none |
| `version=` (empty string) | Latest related version including deleted versions, or root |
| Nonempty integer `version=<id>` | That ID, but only if it is the root itself or a direct version of that root |
| Nonempty non-integer value | DRF `NotFound` → 404 |
| Integer names a missing or unrelated document | 404 |

“Latest” is ordered by `version_index` descending with nulls last, then `id` descending (`src/documents/versioning.py:23-28`, `159-195`).

A present `version` parameter causes the global manager to be used, including for explicit deleted versions. Consequently, adding even an empty `version=` changes the selection from “latest visible” to “latest including deleted.”

### Original/archive representation

Once `file_doc` is fixed:

- `original=true`, exactly and case-sensitively, selects `file_doc.source_file`.
- Otherwise, if `file_doc.has_archive_version` is true, it selects `file_doc.archive_file`.
- Otherwise it falls back to `source_file`.

This occurs at `src/documents/views.py:1368-1373`, `1442-1448`, and `4948-4965`.

For the response:

- Download uses `Content-Disposition: attachment`.
- Archive content type is `application/pdf`.
- Original content type comes from the selected document’s `mime_type`, with charset additions for supported text/CSV types.
- `follow_formatting` changes the response filename choice, not the selected document or file handle.
- A synchronously raised `FileNotFoundError` or `Document.DoesNotExist` is converted to 404 (`src/documents/views.py:1834-1839`, `4941-4995`).

## 2. Authorization checks and their order

The effective order is:

1. **DRF request-level checks.** `dispatch` calls `initial` before the handler; `initial` performs authentication, permission, and throttle checks (`framework/rest_framework-3.18.1/rest_framework/views.py:490-520`, `404-421`).
2. **Global view permissions.** `DocumentViewSet` declares:
   - `IsAuthenticated`
   - `PaperlessObjectPermissions`  
   (`src/documents/views.py:1008-1027`).
3. **Model permission.** For GET, `PaperlessObjectPermissions` maps to `documents.view_document`; inherited DRF logic obtains the model permissions and calls `request.user.has_perms(...)` (`src/documents/permissions.py:30-44`, `framework/rest_framework-3.18.1/rest_framework/permissions.py:203-246`).
4. **Manual request/root lookup.** The action directly retrieves `pk` and resolves the root.
5. **Manual root-object authorization.** For a non-null user, `has_perms_owner_aware(user, "view_document", root_doc)` allows when:
   - the root is unowned;
   - the user owns the root; or
   - Guardian’s `ObjectPermissionChecker.has_perm("view_document", root_doc)` allows.  
   Otherwise `file_response` returns 403 (`src/documents/views.py:1417-1427`, `src/documents/permissions.py:624-635`).
6. **Only after that check** does the action select the effective version, choose original/archive, and construct the file response (`src/documents/views.py:1429-1448`).

`ObjectPermissionChecker` is constructed before the owner/unowned short-circuit expression. Its `has_perm` method is only reached when neither ownership shortcut applies.

The action does **not** use DRF’s `get_object()` or call `check_object_permissions()` for either the requested row or selected `file_doc`. Consequently, the inherited `PaperlessObjectPermissions.has_object_permission` path is not invoked for the selected version. The controlling object-specific check is the explicit check on `root_doc`.

The source also contains a `request.user is None` branch that skips the manual root check. In an ordinary request, `IsAuthenticated` should reject such a caller before the action; the finite program does not evaluate or prove that upstream outcome.

## 3. Does alternate selection change the authorized resource?

Generally, **no**:

- If `pk` names a root, authorization is evaluated on that root.
- If `pk` names a version, authorization is normally evaluated on its resolved root; with no `version` parameter, the requested version itself is then returned.
- An explicit version ID may switch `file_doc` to the root or another direct version, including a deleted one, but the authorization target remains the already-checked root.
- The selected version can have a different `owner` from the root. That owner is not checked again.
- An unrelated explicit version is rejected with 404 rather than changing the authorization target.
- Choosing original versus archive only changes which file field is opened on `file_doc`; it does not change the checked object.

The exceptional root-resolution fallback is when a row has a root ID but the root cannot be obtained: the requested row itself becomes `root_doc` and therefore the authorization target (`src/documents/versioning.py:146-156`).

Thus the source establishes a **root-centric authorization model followed by version/representation selection**. Without the intended ownership semantics for versions and actual grants, this alone does not establish an authorization vulnerability.
