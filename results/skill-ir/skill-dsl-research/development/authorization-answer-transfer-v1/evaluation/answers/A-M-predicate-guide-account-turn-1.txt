## Source behavior

### Token-to-memo binding

`GetSharedMemo` does not accept a memo identifier independently of the token:

1. It looks up `request.ShareToken` as `MemoShare.UID`.
2. It rejects a missing or expired share.
3. It loads the memo using that share row’s `MemoID`.

Consequently, a caller cannot combine a valid token with a different memo ID through this request. The database share row determines the memo.

Sources: `server/api/v1/memo_share_service.go:172-185`, `:216-229`.

Expiration is strict:

```go
time.Now().Unix() > *ms.ExpiresTs
```

Thus a token with `ExpiresTs == now` remains valid for that second; it expires once `now` becomes greater.

### Invalid and expired tokens

Both cases produce the same generic result:

- Missing token: `NOT_FOUND: "not found"`
- Expired token: `NOT_FOUND: "not found"`

This deliberately avoids disclosing whether a share existed. A share-store failure is different: it becomes `INTERNAL: "failed to get memo share"`.

Source: `server/api/v1/memo_share_service.go:221-229`.

### Additional controls on a valid token

Even a valid, unexpired token is rejected with generic `NOT_FOUND` when:

- The bound memo is missing.
- The memo is not `NORMAL`—including archived memos.
- Its visibility is `SPACE`.
- Its visibility value is structurally unknown.
- Its creator is missing or not `NORMAL`/`ARCHIVED`.
- Building the read context fails.
- The final read decision is not allowed.

Sources:

- `server/api/v1/memo_share_service.go:178-189`
- `core/access/memo_resolve.go:31-52`
- `core/access/memo.go:87-122`

Store failures differ by stage:

| Failure | Visible result |
|---|---|
| Share lookup | `INTERNAL`, failed to get memo share |
| Memo lookup | `INTERNAL`, failed to get memo |
| Viewer/instance policy/creator/space/membership resolution | Hidden as generic `NOT_FOUND` |
| Reaction listing | `INTERNAL`, failed to list reactions |
| Attachment listing | `INTERNAL`, failed to list attachments |
| Missing creator during conversion | Generic `NOT_FOUND` |
| Other conversion failure | Wrapped conversion error |

### Unauthenticated access

The endpoint itself requires no authentication. For an unauthenticated caller, `buildMemoReadContext` resolves the instance’s anonymous-access setting. However, the shared-memo policy then computes:

```go
shareApplies :=
    ctx.SharedMemoID != nil &&
    memo.ID == *ctx.SharedMemoID &&
    memo.Visibility != store.SpaceAudience
```

A structurally valid exact-memo share is allowed before the ordinary PUBLIC/PROTECTED/PRIVATE audience branches. Therefore:

- A valid share can expose a `PRIVATE` memo to an unauthenticated caller.
- This remains true when the instance access mode is `PRIVATE`.
- The instance-setting lookup must still complete successfully; its Boolean result does not override the exact-share branch.
- Authentication, authorship, or Space membership is not required for that exact shared memo.

Sources:

- `server/api/v1/memo_access.go:17-40`
- `store/instance_setting.go:255-262`
- `core/access/memo.go:92-145`

### What the token exposes around the memo

On success, the response includes the bound memo plus:

- Reactions selected by that memo’s ID.
- Attachments selected by that memo’s ID.
- Converted creator and memo fields.

But it deliberately excludes graph expansion:

- Relations are passed as `nil`, and conversion emits an empty relation list.
- Conversion may initially set `Parent` from `ParentUID`, but `GetSharedMemo` explicitly resets it to `nil`.
- The share policy applies only where `memo.ID == SharedMemoID`; it does not transfer to a parent, child, relation endpoint, or conversation graph.

Sources:

- `server/api/v1/memo_share_service.go:191-213`
- `server/api/v1/memo_service_converter.go:26-103`
- `core/access/memo.go:87-122`

This establishes inclusion of reaction and attachment data in this memo response. It does **not** establish independent download, mutation, or separate-endpoint rights for those resources.
