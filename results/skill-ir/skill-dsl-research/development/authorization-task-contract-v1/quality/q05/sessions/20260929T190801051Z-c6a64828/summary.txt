Conclusions
- scenario%3Aversion-owner-no-root-view::entry%3Adownload: source_refuted — At the declared download entry, the handler dispatches to file_response. Before selecting or serving a file, file_response resolves the request document and its root document, then applies has_perms_owner_aware to the root document with the view_document permission. Under the stated premises, the caller is not the root owner and has no object view grant, so this owner-aware check fails and returns HttpResponseForbidden. Thus the requested version's ownership does not independently authorize the download. If the gate were passed, the effective file object for a version request would be resolved from the root by _get_effective_file_doc/_resolve_file_doc and passed as doc to serve_file; in the stated scenario that serving effect is not reached. The source therefore denies this scenario at the declared-entry boundary and aligns with the accepted policy requiring the root-document check before serving any selected version. This conclusion is limited to the supplied source ranges and stated premises; no additional repository or deployment facts are used.
