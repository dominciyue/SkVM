## 1. 请求文档与返回文件

路由把该资源放在 `documents` 前缀下；`download` 是 GET detail action，随后以 `attachment` 调用 `file_response`（`src/paperless/urls.py:74-77`；`src/documents/views.py:1834-1839`）。

处理次序如下：

1. `pk` 使用 `Document.global_objects` 查找，因此请求文档本身可以是已删除记录；找不到则 404。
2. 如果请求文档已经是版本，解析其根文档；否则它本身就是根文档（`src/documents/views.py:1401-1427`；`src/documents/versioning.py:146-156`）。
3. 对根文档完成 action-level 授权后，才选择实际文件文档（`src/documents/views.py:1429-1448`）。
4. 若 `pk` 指向版本且 `version` 参数缺失/为 null，直接返回该请求版本。
5. 其他情况：
   - 缺失或 null：选择最新**可见**版本；
   - 空字符串：参数存在，所以查询包含已删除版本；由于空串为假，选择最新版本；
   - 真值字符串：转为整数并选择根文档本身或其直接版本；
   - 候选不存在或不属于该根：404；
   - 无法转成整数：`Invalid version parameter` 的 NotFound。
6. 最新版本排序为 `version_index DESC NULLS LAST, id DESC`；没有版本时回退到根文档（`src/documents/versioning.py:23-28,159-195`）。
7. 文件文档确定后：
   - `original` 的值严格等于字符串 `"true"`：返回 `source_file`；
   - 否则，若该文档有 archive：返回 `archive_file`；
   - 否则仍返回 `source_file`（`src/documents/views.py:1368-1373,1437-1448`）。
8. archive MIME 固定为 `application/pdf`；original 使用文档 MIME，并可能附加 UTF-8 charset。`follow_formatting` 只影响下载文件名，不改变文件句柄（`src/documents/views.py:4941-4995`）。

## 2. 授权检查及其顺序

在 action 执行前，DRF 依次完成认证、全局 permission 和 throttling（`framework/rest_framework-3.18.1/rest_framework/views.py:404-421`）。

`DocumentViewSet` 配置：

- `IsAuthenticated`
- `PaperlessObjectPermissions`

见 `src/documents/views.py:1008-1021`。

对 GET，`PaperlessObjectPermissions` 要求模型权限 `documents.view_document`；DRF 的模型 permission 会调用实际用户的 `has_perms`（`src/documents/permissions.py:30-44`；`framework/rest_framework-3.18.1/rest_framework/permissions.py:233-246`）。

进入 action 后还有一次自定义根文档检查：

- `request.user is None`：此 action-level 检查短路跳过；
- 根文档无 owner：允许；
- 根文档 owner 是当前用户：允许；
- 否则调用 Guardian `ObjectPermissionChecker.has_perm("view_document", root_doc)`；
- 返回 false 时得到 403（`src/documents/views.py:1421-1426`；`src/documents/permissions.py:624-635`）。

随后才解析 `file_doc`，并直接调用 `serve_file`。代码没有对 `file_doc` 调用 `get_object()` 或 `check_object_permissions()`。通常 DRF 的 `get_object()` 会调用后者，但 Download 走的是自定义查询路径（`framework/rest_framework-3.18.1/rest_framework/generics.py:79-105`；`src/documents/views.py:1429-1448`）。

## 3. 替代版本和 original/archive 是否改变授权资源

**不会。**

授权资源始终是由请求文档解析出的 `root_doc`。版本选择发生在根文档检查成功之后：

- `pk` 指向版本时，授权目标仍是它的根文档；
- `version=<id>` 改变的是授权后选出的 `file_doc`；
- 最新可见、最新含删除记录以及明确版本分支都不替换授权目标；
- `original=true` 或 archive 分支只改变最终文件句柄、MIME 和文件名；
- 选中的版本可能具有不同 owner，但源码没有再次对该版本执行 owner-aware/object permission 检查。

有限默认输入正好表现为：授权根 `10`（owner 7），随后返回版本 `11`（owner 9）的 archive。

## 4. 缺失事实和条件结论

以下事实没有由源码或有限输入提供：

- **真实认证结果及 `documents.view_document` 模型权限**：因此不能断言某个部署用户一定能进入 Download action。
- **真实根文档 ownership 与 Guardian grant**：因此不能断言一个非 owner 用户会被允许；只有提供精确 `has_perm(user, root, permission)` 事实后才能计算。
- **真实数据库内容、删除状态和版本关系**：因此有限 fixture 的文件 ID 不能外推为部署结果。
- **存储后端、文件存在性和可读性**：因此即使授权和选择成功，也不能断言文件流一定能打开。`download` 仅把可见的 `FileNotFoundError`/`Document.DoesNotExist` 转为 404（`src/documents/views.py:1834-1839`）。
- **部署代理及外部 URL 前缀**：源码可建立 router/action 关系，但不能确定公开部署 URL。
- **Malformed truthy version 的可执行建模**：源码结论明确是 NotFound，但当前有限表达式中的整数转换仍可能表现为 unresolved；这是剩余的程序作者工作，不能用虚构结果填补。

程序仍保留概括性的“尚有源码分支待审阅”覆盖缺口，因此这是已修复、可回归执行的持久草稿，而不是对所有部署事实的授权证明。
