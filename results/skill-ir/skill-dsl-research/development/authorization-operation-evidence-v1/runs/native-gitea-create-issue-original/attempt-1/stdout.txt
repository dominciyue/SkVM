**Severity:** 🟠 HIGH  
**Confidence:** Medium  
**Category:** Authorization / missing function-level access control  
**Policy status:** **Violated by the source-visible path; deployment qualification remains unresolved**

### Source behavior

The route-level control shown in the registration is:

```text

```

That is a repository **reader** control for the issues unit.

Inside `CreateIssue`, `CanWrite(unit.TypeIssues)` is used for optional deadline handling and writer-only metadata processing. The relevant permission implementation is:

```go
func (p *Permission) CanWrite(unitType unit.Type) bool {
    return p.CanAccess(perm_model.AccessModeWrite, unitType)

```

`CanAccess` compares the effective unit access mode against the requested mode:

```go
func (p *Permission) CanAccess(mode perm_model.AccessMode, unitType unit.Type) bool {
    return p.UnitAccessMode(unitType) >= mode
}
```

`UnitAccessMode` derives access from configured unit permissions, administrative/owner access, or repository/anonymous/everyone defaults:

```text
models/perm/access/repo_permission.go:97-108
models/perm/access/repo_permission.go:119-121
models/perm/access/repo_permission.go:153-155
```

However, based on the reviewed `CreateIssue` path:

1. The route admits a caller through `reqRepoReader(unit.TypeIssues)`.
2. `CanWrite(unit.TypeIssues)` is consulted for deadline and metadata behavior.
3. A caller failing the metadata write check is not necessarily rejected; the non-writer branch clears labels and continues.
4. `NewIssue` is then called at `routers/api/v1/repo/issue.go:624`.
5. The reviewed `services/issue/issue.go:25-84` path performs poster loading, blocked-user handling, persistence, and related issue work, but no issues-unit write authorization check was shown before persistence.

Accordingly, the source-visible control flow permits this conditional path:

```text
authenticated caller
  -> passes issues-unit reader middleware
  -> lacks issues-unit write permission
  -> reaches CreateIssue
  -> metadata is restricted or cleared as applicable
  -> NewIssue is called
  -> issue may be persisted if validation and operation succeed
```

### Risk

If the route shown at `api.go:1649` is the effective deployed route and no upstream control adds a writer check, a principal with only repository/issues read permission could create an issue.

That would violate the independent policy because:

- **Read access** is used to enter the route.
- **Write access** is not demonstrated as a prerequisite for the `NewIssue` effect.
- The handler’s `CanWrite` checks appear to control optional fields and metadata, not whether issue creation itself occurs.

### Relevant exceptions and rejection paths

These conditions can still prevent creation, but they are not substitutes for the required issues-unit write authorization:

- The caller may fail authentication or route middleware.
- The repository may be archived.
- Assignee validation or other request validation may fail.
- A poster blocked by the repository owner or assignees may be rejected.
- Persistence or related-data operations may fail.
- Unshown middleware may add a writer check.
- Deployment-specific permission construction may differ from the source assumptions.

These are operational or separate authorization exceptions; none of the reviewed `CreateIssue`/`NewIssue` source establishes the policy-required write check around the creation effect.

### Recommended remediation

Add an explicit issues-unit write guard to the effective route or immediately before the creation service is invoked. The guard must deny callers who have only read access.

Conceptually:

```go
// Require issues-unit write permission before performing the creation effect.
if !ctx.Repo.Permission.CanWrite(unit.TypeIssues) {
    ctx.Error(http.StatusForbidden, "issue creation requires write permission", nil)
    return
}

err := issue_service.NewIssue(ctx, ctx.Repo.Repository, issue, ...)
```

Alternatively, replace the route-level reader middleware with the corresponding repository issues-unit writer middleware, provided that middleware is the authoritative control for this operation.

**Review each patch before applying. Nothing has been changed.**
