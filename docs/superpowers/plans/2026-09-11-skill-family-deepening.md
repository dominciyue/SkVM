# 夜间持续执行任务书：一类 skill 的自动化能力深化

> 2026-09-11 用户修订：今晚优先深化项目、获取真实外部 skill、改进通用构造能力和验证类内迁移。本文取代旧 deadline 任务书的执行队列；HTML、用户入口包装、演示讲稿和论文润色不再是今晚任务。本文制定时尚未执行本队列。

**Goal:** 对一个独立于当前实现定义的 skill 类，建立真实成员与完整职责分母，开发可被多个成员复用的构造/核验能力，并在未参与改进的同类 skill 上检验效果。

**Architecture:** 复用现有 skill-loader、职责家族合同、普通 API 输入执行链、构造器和独立 checker。补齐真实 skill → 有依据的职责合同 → 声明式能力映射 → 确定性产物的连接；根据多个 skill 的共性缺口改进共享实现。不得按 skill 名称或仓库写专用成功分支。

**Tech Stack:** 现有 Bun/TypeScript、GitHub CLI、JSON/CSV、现有模型客户端；Markdown 只记录必要设计、实验解释和恢复步骤。不新增前端或通用编排平台。

## 2. “一类 skill”是主验收对象

### 2.1 先明确候选类，再检验是否成立

上位职责家族继续使用现有 public-structure offline family 合同。今晚优先深化的候选子类暂定为：

**以公开 API 合同为输入，按明确覆盖要求构造可独立核验的离线测试产物的 skill。**

该类的成员判断依据是 skill 原文及资源中声明的输入、输出、规则和依赖，而不是程序能否 accepted：

- 有明确可定位的 API 合同输入及其版本/依赖。
- 目标职责明确要求生成测试用例、请求用例集合或其他可以对照公开合同核验的离线测试产物。
- 测试义务与正确性边界能明确表达；若语义选择尚未界定，标不确定，不假装确定。
- 构造阶段的外部效应、资源与依赖可以界定；真实业务断言、探索式渗透、线上状态推理不默认为已覆盖。

成员资格、可验证性、可构造性、当前支持和外部验证结果必须分列。nested object、组合 schema、外部引用等暂不支持特性，不能自动成为移除成员的理由。

本名称是待外部正文验证的候选类，不宣称已经建立完整分类学。如果真实来源不足或共同职责无法统一，保留失败与边界分析，在上位家族内修订概念；不能为了凑数把三个 API 文档改称三个 skill，也不在一夜之间另起无关领域的编译器。

### 2.2 区分整类 skill、职责切片和输入

数据链至少记录：`repository/commit/SKILL.md → skillId → responsibilityId → task contract → inputId → artifact/checker result`。

同一 skill 的多个 API 文档只增加输入分母；同仓库/复制模板/同源 fork 不作为独立 skill 迁移证据。

对复合 skill 记录全部可识别职责和未确认部分：若仅完成测试构造职责，结论是“同类职责切片可复用”，不是整个 skill 自动化。不得无依据地把 `completeScope:true` 填满；现有机器合同要求完整范围时，先完成原文核对，未完成的记录留在提取草稿中，不伪造完整输入。

### 2.3 什么才叫“对这一类有效果”

本轮追求以下证据，未达到时逐项说明，不能用产物数量替代：

1. 类的成员判据能脱离当前支持表说明；含正例、反例和属于该类但尚不支持的例子。
2. 目标至少 3 个独立 development skill 共用一套构造/检查实现。新增成员只需公开输入与声明式参数；若必须写语义代码，记录工程适配量，不能称零适配。
3. 每个被测 skill 目标至少 2 个适用任务输入，分别保留完整职责、任务输入和操作分母。不同 skill 的不适用义务显式标记，不能擅自删掉困难义务。
4. 支持扩张来自多个成员的共性需求；输出必须满足独立检查，并检验合法输入被不必要拒绝的问题。
5. 改进后固定方法，再取得目标至少 3 个未参与开发的同类 skill 作外部检验；同源复制不算独立。测试中发现问题可转入下一轮开发，但首跑保留。
6. 记录任务质量、完成的职责/义务覆盖、构造耗时、运行时调用和加入新 skill 所需修改；有可比原 skill/模型执行时再给效率与成本对照。单有 0 token 或 accepted 上升不算效果成立。

有限样本不能证明“自然语言描述的整类所有未来 skill 永远成功”。工程侧要做到：明确支持合同、逐产物独立核验、超界拒绝；研究侧要展示多个独立成员和新成员上的实际效果。缺失的完整性/泛化证据保留为缺口，不缩小类来隐藏。

### D2：类定义、职责分解与实例清单（约 1.5–2 小时）

- [ ] 阅读实际正文，将成员/非成员/不确定与判断原文位置对应；检验第 2 节候选类是否真实存在，而非只在项目内定义。
- [ ] 深读目标 6–10 个相关 skill 的职责与直接依赖，建立 skill→完整已识别职责→构造义务表。不能只摘最容易自动化的一句。
- [ ] 复用 family contract，分别记录公开 oracle 是否充分、构造证据是否充分、源有效性/依赖/语义选择与当前支持。负例解释应指向具体缺失条件。
- [ ] 若模型参与提取，输出有原文定位的结构化草稿；确定性校验字段/定位，针对争议例核读原文。没有真实人工不得产出真人一致率或人工节省。
- [ ] 写一份短 `family-contract.md` 与 `skill-responsibilities.json`；变更成员判据要记录理由，不能随着 accepted 结果删除失败成员。

验收：有独立于实现的类边界、真实成员及完整性限制；数据单位明确区分 skill/职责/输入/操作。

### D3：搭通 skill 职责到共享执行能力的连接（约 2 小时）

- [ ] 从 D2 按成员规则选目标至少 3 个独立 skill；先记录各自输出要求和可验证义务，再配置任务输入。
- [ ] 建立最小声明式职责映射，复用现有 loader、family contract 和普通输入 runner。映射只声明输入位置、格式、义务和现有 profile，不允许嵌入按仓库专用的答案或构造代码。
- [ ] 映射由人/代理/模型建立均如实记录。允许 AOT 阶段模型辅助合同提取，但提取完成不能自动视为语义正确；有依据且通过核验的合同才进入确定性执行。
- [ ] 若使用机器自动提取，要单列“提取是否成功”和“合同确认后执行是否成功”；不能把手工写好映射后的运行冒充任意 SKILL 自动接入。
- [ ] 先做一个真实成员端到端，再加另外成员验证共享性。聚焦测试覆盖缺失资源、错误字段绑定、额外未覆盖职责和 skill 名称变化不影响构造行为。

验收：真实 skill 的职责能追踪到实际执行与产物；加入成员的代码/配置修改量可见，未支持部分没有被隐藏。无需 HTML 或新的用户交互入口。

### D4：跨 skill 基线、输入覆盖和瓶颈定位（约 1–1.5 小时）

- [ ] 对 D3 的每个成员准备目标至少 2 个与原职责匹配的真实任务输入；公共 API 文档总目标约 12 份、覆盖约 6 个来源。不能给每个 skill 随意塞同一文档而不核对职责。
- [ ] 运行前记录代码版本、输入列表、超时和失败分类；使用全部候选成员/输入，不按 accepted 选样。旧 exposed/recovered 输入单列。
- [ ] 复用现有操作清单、checker 和 coverage 输出，统计按 skill/职责/输入/操作的分布；校验失败、构造拒绝、source blocker 和基础设施失败分开。
- [ ] 形成“缺失能力→受影响的 skill/职责/输入→可构造性依据→实现/核验难度”排序。优先跨至少两个独立成员出现的共性缺口；只在一个例子出现的特性不能伪称全类需求。

验收：可以从实际失败定位应修改的共享组件。样本不够独立时补 D1/D2；不能继续只围绕旧六份文档证明同一结论。

### D5：实现最有价值的共享能力缺口（约 3–4 小时，核心）

- [ ] 从 D4 排序选一个第一优先能力，完成后再做一个不同但相关能力；目标 1–2 项真正完成的改进，不以数量强迫完成高风险复杂特性。
- [ ] 候选方向包括嵌套对象/数组的约束构造、受限组合约束、引用与依赖闭包、必要序列化/format witness；具体选择由 D4 的真实跨 skill 需求决定。不能脱离数据提前承诺某特性必做。
- [ ] 每项半页写清输入语义、生成规则、支持边界、终止/资源界限和独立 checker 义务；记录资料依据。先真实最小失败例，再实现构造和检查。
- [ ] 建立有效 witness 的检查、非法边界例、漏字段/改约束等有针对性的错误注入。checker 不能复用生成器的取值函数充当唯一 oracle；优先使用可适用的独立标准实现或从源合同独立评估。
- [ ] 对相关数据做一次前后比较，报告多个 skill 中的新增完成职责、义务覆盖、无必要拒绝、校验失败和回归；性能只在语义一致时比较。
- [ ] 若实现需要较大改变，先局部形成可测能力，再接入共享路径；不为旧数据通过而猜补 source blocker，不删除测试义务或降低正确性要求。

验收：共享实现真正扩展能力，有至少两个独立 skill 的适用实例或明确的证据短缺；只改报告计数、包装命令或扩大拒绝条件不算完成该任务。

### D6：把“自动到什么程度”测清楚（约 1–1.5 小时）

- [ ] 固定原 skill 任务描述、公开输入、输出要求及同一独立检查标准；分别测共享确定性路径与可运行的原 skill/模型辅助路径。目标约 6–12 个匹配任务，先小批确认接口可比。
- [ ] 记录首次合同/映射建立是否需要模型、每次新输入是否需要模型、手工/代理改动、构造时间、token/调用/费用、质量及剩余职责。无法实测的人工分钟明确未测。
- [ ] 付费调用可用于有具体价值的合同提取、参考实现、错误归因与公平基线，不要求为了零调用而停工；缓存相同输入结果，不反复试到最好再只报成功。
- [ ] 基线若只在已支持切片可比，则分层报告，不能把该切片效果推广到所有成员。基线无法接通时保留 AOT 实际测量并继续 D7，注明比较缺失。

验收：明确效果是质量、覆盖、确定性执行、接入改动还是成本中的哪一项；不能仅用“产物 checker-pass/0 token”声称整个 skill 自动化成功。

### D7：固定改进版后测试新同类 skill（约 2 小时，主验收）

- [ ] 在读取新增测试成员正文前，固定类判据、实现版本、映射规则、抽取提示（如有）、任务生成/选择规则和报告指标。一次简短方法记录即可，不要求多次远端冻结。
- [ ] 按预定发现顺序取得目标至少 3 个此前未参与 D2–D6 的独立同类 skill，优先新的独立仓库；重复来源与以前读过的正文如实归 development。获取失败/不属于类/成员资格不确定分开记录。
- [ ] 每个新增成员目标至少 2 个实际适用输入。允许按固定规则生成声明式配置，但不改核心代码、增加专用分支或人工补答案后称首跑成功。
- [ ] 分别统计类内资格、映射接入、构造、独立检查、完整职责覆盖、原任务输出符合性及改动量。所有同类失败成员留在分母。
- [ ] 已知正式支持合同内的误拒绝、错误产物和跨成员漂移是缺陷；类内但合同外的功能列为覆盖缺口，不将两者混写。
- [ ] 测试中发现问题先保存首跑，再进入下一轮 development 修复；需要新泛化结论时重新固定并取得新成员，禁止反复用已暴露测试集自称外部首跑。

验收：得到“这一类能迁移到哪些新成员、失败在哪里”的真实结果。若没有新成员通过，目标的类内效果部分尚未达成，继续处理技术缺口；不能仅因生成结果文件而宣布完成。

### D8：必要工程优化与回归（约 1 小时）

- [ ] 从 D3–D7 的实际运行中选择一个有证据的工程瓶颈：重复解析/引用展开、同源重复下载、批处理失败隔离或接入重复代码。没有瓶颈不为优化而重构。
- [ ] 修复并在相同输入、相同结果语义下比较；缓存需考虑输入变化，不能复用过期产物。不要削弱 checker 换耗时。
- [ ] 完成受影响聚焦回归、一次 typecheck、真实成员端到端复现和 diff 检查。只对新失败重跑相关项，不逐层复核全部历史归档。

验收：可用共享代码和必要测试；性能结果有基线，不能凭感觉声称优化。

### D9：轻量工程交接与推送（约 20–30 分钟）

- [ ] 保存来源/职责/首跑/改进/新成员测试结果及最短重现命令；数据可以是 JSON/CSV，结论说明只写理解下一步所需内容。
- [ ] 同步实际修改组件的说明、当前状态与 handoff。记录完成、失败、未执行及剩余类内缺口，不生成论文、PPT、HTML 或演示脚本。
- [ ] 按功能提交并推送用户 origin 当前分支。保留历史实验与用户未跟踪材料，不自动合并主分支。
