# 9 月 5 日至 9 月 14 日工作汇报

口径：截至 2026-09-14，综合这十天内的开发记录与当前实现。早期 API 工具是此前研究的延续，不将全部基础工作都算作十天内从零完成。不同阶段样本有重叠，不能合并成统一成功率。

## 可直接使用的汇报稿

这十天，我主要把项目从受限场景的 skill 优化实验，推进到了真实运行驱动的通用优化工程。现在的目标可以用一句话概括：用户正常运行一次 skill，系统自己记录执行过程，找到其中可以复用或程序化的步骤，生成一个保留原有职责、带有局部程序和使用说明的新 skill 包。

前期的 API 合同工作已经形成可复用基础。在六份公开 API 文档的 562 个操作中，系统接受了 112 个操作，这些操作的产物全部通过对应检查，覆盖 575 项验证义务。不过整份文档仍没有全部通过，所以这证明的是受限操作级自动化能力，不能说任意 API skill 已经完全自动化。

在此基础上，我结合多种公开 skill 和真实 trace，把优化流程从修改说明文档扩展到了程序复用、程序生成、原始输入捕获、局部验证、自动修复和独立包导出。已有一轮广读了 30 份 development skill，其中 10 份深入分析，用来比较共同的机械步骤和需要保留给 agent 的语义职责。目前用户不需要自己准备 trace 或研究用的评分文件，普通入口已经能够自动采集和交接。

最近一轮完成了五次真实普通入口尝试，其中一次由优化器生成了新的非 API 参数化检查程序，并在原任务和变化任务中被普通 agent 实际调用。这说明系统已经不只是压缩 SKILL.md，而是能够把一部分工作真正交给程序。但该新包的默认内部行为验证仍是未运行状态，后续消费验证是在另外组织的环境里完成的，所以还不能称为稳定成熟的全自动生产流程。

效果方面已经观察到局部改善，但总体仍是 mixed。例如一组成对实验耗时下降约 57%、输出 token 下降约 76%，输入与缓存读取却增加，总观测 token 反而上升约 61%。因此，我目前不会声称普遍省 token、美元成本或人工时间；要区分程序接管了工作和整体开销真的下降。

下一阶段的重点是补牢通用生成过程：让引擎自动完成有依据的参数和验证接线，避免模型漏填信息就留下未验证草稿；用变化输入检查程序是否写死了路径；依据真实调用观察减少 agent 的重复探索。不同 skill 是验证这些共享能力的案例，不为它们分别写成功分支。当前已经有可运行的研究原型和局部正向结果，接下来要把已有组件变成更可靠、实际更省事的使用流程。
