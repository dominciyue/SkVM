# Skill IR Experiment Design

## Purpose

This document defines the current evaluation plan for Skill IR as an AOT optimization pass in the SkVM skill compilation setting. The active experiment tests source-backed real skills across model families and context conditions on one Windows host and one global adapter. Agent and real-OS generalization remain planned axes until the runner actually switches harnesses and hosts.

The design follows the Task 7.5 literature calibration:

- Evaluate systems on paired cases instead of unrelated aggregate runs.
- Include `no-skill` and `original` baselines before optimized systems.
- Track negative deltas and regressions, not only average gains.
- Treat checker lowering as a declarative/checkable specification; independent runtime enforcement is future work.
- Treat profile-guided repair as typed trace feedback.
- Treat adapter lowering as an agent-computer interface layer.

## Research Questions

1. Does Skill IR improve mean and worst-case task success across tested model families and contexts?
2. Does Skill IR improve worst-case success?
3. Does Skill IR reduce variance across settings?
4. Which optimization pass contributes most to reduced rule violations and skipped required steps?
5. How often does an optimized system regress relative to the original skill on paired cases?
6. Does task-local PGO generated from development failures improve disjoint held-out tasks without regressions?
7. Which repeated operations can later be solidified into a validated reusable artifact package?

## Systems Compared

The complete-claim report uses four systems, but it is produced in two stages:

| System | Name | Description |
|---|---|---|
| S0 | `no-skill` | Agent receives the task without the target skill. |
| S1 | `original` | Agent receives the original natural-language skill. |
| S2 | `ir-static` | Skill IR with validation, rule normalization, environment guards, and lowering. |
| S3 | `ir-pgo` | Task-local PGO IR generated only from development feedback and evaluated on disjoint held-out tasks. |

Supported but non-default systems are `ir-only` for explicit ablation, `ir-profile` for archived-run compatibility, and `skvm-aot` as a stub that must not enter the main table until connected to a real upstream AOT path.

Cold-start scheduling contains only `no-skill | original | ir-static`. After `original × development` evidence compiles a provenance-bearing Final IR, an explicit held-out run adds `ir-pgo`. The fourth column is never a default or a stand-in for unchanged base IR.

`original` is the default baseline for paired delta calculations that ask whether Skill IR improves a provided skill. `no-skill` is a required baseline for the broader question of whether the skill should be applied at all. Real-agent experiments should include `no-skill` whenever budget allows, especially before claiming that skill optimization improves stability.

If `no-skill` outperforms skill systems on a task shape, the result should not be hidden as an anomaly. It can mean:

- the original skill is too broad;
- the task does not need the skill;
- the skill adds token/context noise;
- the right optimization is skill routing or skill narrowing, not stronger IR materialization.

## Paired Evaluation Unit

The core paired unit is:

```text
caseId = skill:agent:environment:context:task
```

All systems for the same skill, agent, environment, context, and task share the same `caseId`. This lets the analyzer compute deltas and regressions against the baseline on exactly matched conditions.

The benchmark matrix is generated by:

```text
src/benchmarks/skill-ir/matrix.ts
```

The cold-start calibration scheduling upper bound is:

```text
6 skills x 2 agent labels x 2 environment labels x 4 contexts x 4 tasks per skill x 3 systems = 1152 scheduled cases
```

This count describes scheduling only. Because labels do not currently select distinct adapters or hosts, it is not evidence for two agents or two environments. Real pilot runs should avoid duplicate label-only cells and pass the actual adapter/host in run metadata.

Tasks are bound to their owning skill through `tasksBySkill` in the matrix input. The flattened `tasks` list is only a compatibility/reporting view. The matrix must not pair one skill with another skill's task, because that would create artificial failures and inflate the apparent benchmark scale.

This seed corpus is retained for calibration only. The active evidence track uses three Wave A deep real-skill pilots and three mandatory Wave B replication pilots.

## Skill Selection

The earlier scale targets are archived aspirations, not current gates. The active pilot is:

| Layer | Current Count | Purpose |
|---|---:|---|
| Deep pilots | 3 | Full source/no-skill/IR/development/held-out evidence. |
| Wave B replication pilots | 3 mandatory | Test a frozen Wave A method across different categories and languages. |
| Synthetic seeds | 6 | Low-weight pipeline and scorer calibration only. |

Skill categories should cover:

- workflow
- tool-use
- constraint-heavy
- diagnostic
- generative
- environment-sensitive

Task count follows scorer quality and task-family coverage, not an old fixed quota. Every pilot needs enough development cases to generate documented feedback and disjoint held-out cases to test generalization; Wave B data must not tune the same reported configuration.

Each skill should record `skillPackaging`:

```text
focused | broad | unknown
```

Focused skills are preferred for early evaluation because broad skill bundles can confound whether gains come from better instructions or simply more documentation.

Each skill should also record provenance:

```text
synthetic-seed | adapted-public | real-public | upstream-skvm | user-provided
```

The current seed corpus is mostly `synthetic-seed`. It is appropriate for pipeline construction and controlled case studies, but broad claims need a larger set of externally sourced or user-provided skills. The next corpus expansion should include upstream SkVM skills, public agent skills, non-coding workflows, bilingual or Chinese skills, schema-heavy output skills, and environment-sensitive tool skills.

Evidence should be weighted by provenance. Synthetic seed rows should be treated as low-confidence calibration evidence unless they are reported as a separate controlled case study. Main stability claims should be made on `real-public`, `adapted-public`, `upstream-skvm`, or `user-provided` rows, with provenance counts included in every aggregate table.

The initial real-skill intake prioritizes `anbeime/skill`, then supplements with `laolaoshiren/claude-code-skills-zh`. `travisvn/awesome-claude-skills` is a backup discovery index and does not count as evaluated evidence by itself. The 2026-07-15 audit followed its scientific-skills entry to the real MIT-licensed `K-Dense-AI/claude-scientific-skills` repository.

The first licensed pilot is:

```text
law-to-markdown
zh-code-reviewer
api-tester
env-manager
zh-readme
experimental-design
```

The machine-readable intake snapshot is `benchmarks/skill-ir/corpus/real-skill-intake.json`. It fixes source commits and records artifact completeness, license scope, dependencies, risks, and artifact-solidification potential. This pilot is the input to the next IR-conversion stage; it is not yet evaluated evidence.

## Context Conditions

The standard context perturbations are:

| Context | Meaning |
|---|---|
| `clean` | Only the task and skill are provided. |
| `noisy` | Distracting or adjacent but incorrect information is included. |
| `long` | Long surrounding conversation or repository context precedes the actionable request. |
| `compressed` | Prior context has been summarized and may lose details. |

These conditions test the original motivation: natural-language skills behave differently across contexts, while optimized Skill IR should preserve core workflow and constraints more consistently.

## Tested And Planned Axes

Currently tested:

```text
model family x context x skill x system
host: Windows
adapter: one global adapter selected per run
```

Planned after the real-skill pilot:

- distinct agent harnesses selected by `agent`;
- Linux/macOS/Windows hosts selected by `environment`;
- WSL or containers when their boundary is recorded explicitly.

Until then, `agent` and `environment` are case metadata and must not be interpreted as executed axes.

## Metrics

The result analyzer currently computes:

| Metric | Source | Meaning |
|---|---|---|
| `mean_success` | result JSONL | Average task success for a system. |
| `worst_case_success` | result JSONL grouped by setting | Minimum success rate across agent, environment, and context settings. |
| `variance` | setting-level success rates | Stability across settings. |
| `rule_violations` | result JSONL | Total runtime or judge-detected rule violations. |
| `paired_cases` | `caseId` matching | Number of cases compared against the baseline. |
| `paired_delta_success` | paired comparison | Mean success delta against baseline. |
| `regression_count` | paired comparison | Baseline succeeds while this system fails. |
| `negative_delta_count` | paired comparison | Single-case success delta below zero. |

Additional metrics to collect during full evaluation:

- Step Coverage
- Required Step Skip Rate
- Token Cost
- Tool Calls
- LLM Calls
- Latency
- Human Correction Count per IR
- Checkable Rule Ratio
- Environment Guard Coverage

Token and latency are secondary diagnostics in the current study. Lower token cost is only a win when task success and rule compliance are preserved. The engineering roadmap distinguishes prompt-token reduction from artifact solidification:

- reusable runtime checks;
- cached environment probes;
- compiled adapters;
- output schemas;
- generated code or templates;
- fixed command plans.

The project will not make a primary token-saving claim before reusable artifacts are actually packaged and reused. The future claim to test is that repeated reasoning, tool setup, schema generation, or code generation can be compiled into reusable artifacts.

AOT optimization may cost more during import or the first few runs. Reports should therefore use amortized token metrics:

```text
total_original(N)  = original_runtime_cost * N
total_optimized(N) = compile_cost + profile_cost + optimized_runtime_cost * N
break_even_N       = smallest N where total_optimized(N) <= total_original(N)
```

Once package reuse exists, a secondary table can include upfront cost, steady-state per-run cost, break-even invocation count, and post-break-even savings. Current prompt-token rows remain diagnostic and cannot establish break-even.

## Artifact Maturity Metric

The current `final IR` and `ir-pgo` artifacts should be evaluated as research artifacts, not as finished reusable packages. The project should track maturity:

| Level | Meaning |
|---|---|
| L0 | Natural skill text. |
| L1 | Structured workflow IR JSON. |
| L2 | Lowered controller/checker/adapter/schema artifacts. |
| L3 | Stable reusable code/file/template/tool-plan blocks. |
| L4 | Validated Skill Artifact Package with authoritative IR, generated skill view, reusable artifacts, provenance, and validation evidence. |

Current results mostly demonstrate L1 and early L2 behavior. Later experiments should measure whether artifact solidification reaches L3 or L4 and whether repeated invocations become more stable or cheaper.

## Deterministic Verifiers

Every deep benchmark task should include deterministic or semi-deterministic success criteria when possible. Examples:

- Output begins with review findings before summary.
- A required step has trace evidence.
- A forbidden command was not executed.
- A required environment preflight check occurred before tool use.
- A generated artifact contains required fields.

Human judgment can still be used for semantic quality, but deterministic checks should cover the parts that Skill IR claims to make explicit.

## Checker Enforcement Boundary

Current checker lowering emits declarative assertions and recovery instructions that are rendered into agent-facing material. The runner does not independently execute predicates or force actions. Therefore current evaluation can measure check visibility and output/trace compliance, but cannot claim runtime enforcement. A future checker runtime may apply:

- retry
- fallback
- ask-user
- abort
- report

The current `No Checker` ablation tests whether declarative checks add value beyond clearer static instructions. An enforcement ablation becomes valid only after an independent checker runtime exists.

## Typed Trace Feedback View

Profile-guided repair is evaluated as typed trace feedback:

```text
execution trace
  -> profile annotation
  -> generated check or recovery policy
  -> later run behavior
```

The key question is whether repeated observed failures can be converted into stable IR changes that improve later runs without hand-tuning each task.

Task 11C implements the concrete result-feedback path:

```text
scored real-agent result rows
  -> execution traces
  -> profile annotations
  -> profile overlay
  -> final optimized IR
  -> ir-pgo held-out evaluation
```

Rows marked as infrastructure failures are excluded from this path. Development or calibration rows may generate annotations, while held-out rows should evaluate whether those annotations generalize.

Validation should become automated, sampled, and layered instead of requiring a full manual matrix for every imported skill. The target flow is:

```text
static import validation
  -> sampled smoke validation
  -> final IR promotion validation
  -> periodic regression validation
```

Small sampled runs can validate mechanism and non-regression. Quality claims still require held-out paired deltas and should separate calibration replay from generalization evidence.

## Adapter View

Adapter lowering is evaluated as an agent-computer interface layer. It should make tool availability, alternatives, platform notes, and environment assumptions explicit enough that an agent can avoid avoidable platform failures.

Environment-sensitive case studies should separate:

- reasoning failure
- missing tool
- wrong shell or path assumption
- missing fallback
- poor adapter/interface affordance

## Ablations

| Ablation | Removed Component | Question |
|---|---|---|
| Full | Nothing | End-to-end Skill IR optimization. |
| No Profile | Profile annotations and profile-guided repair | Does trace feedback contribute beyond static passes? |
| No Environment Guard | Tool preflight checks and alternatives | Do environment guards improve cross-machine stability? |
| No Checker | Runtime checker artifacts | Does enforcement reduce rule violations or skipped steps? |
| No Rule Normalize | Rule-to-check generation | Are explicit normalized rules necessary? |
| No Adapter | Adapter artifact and platform notes | Are tool/environment interfaces a distinct source of stability? |
| No PGO Feedback | Derived profile annotations from scored results | Does dynamic result feedback improve behavior beyond static `ir-profile` materialization? |

## Analysis Workflow

1. Build experiment cases:

```powershell
bun ./src/benchmarks/skill-ir/run.ts
```

2. Execute systems and write JSONL rows to:

```text
results/skill-ir/main-results.jsonl
```

3. Analyze results:

```powershell
python scripts/analyze_skill_ir_results.py results/skill-ir/main-results.jsonl results/skill-ir/main-table.csv
```

4. Compare:

- mean success
- worst-case success
- variance
- paired delta
- regression count
- rule violations
- step coverage
- token and latency cost

5. Write case studies for representative failures and repairs.

## Case Studies

The report should include at least three case studies:

1. Constraint-heavy skill: show a MUST or NEVER rule becoming a runtime check and reducing violation rate.
2. Environment-sensitive skill: show preflight guard, adapter alternative, and improved cross-platform behavior.
3. Diagnostic or workflow skill: show trace evidence, profile annotation, recovery policy, and improved later run.

Each case study should include:

- original skill behavior
- initial failure
- extracted or generated IR element
- optimized behavior
- metric change
- remaining limitation

## Threats To Validity

- LLM behavior can vary across model versions and provider settings.
- Some success criteria still require human judgment.
- The seed benchmark is small before the deep corpus is populated.
- Current seed skills are mostly locally constructed fixtures, so they may reflect GPT-friendly coding-agent conventions.
- Synthetic seed results can overstate generality if they are mixed into real-skill aggregates without provenance weighting.
- Windows/macOS/Linux coverage may be uneven depending on available machines.
- Broad skills can improve performance by adding more documentation rather than better structure.
- Profile-guided repair can overfit development traces if held-out tasks are too similar.
- A missing or weak no-skill baseline can make a harmful or unnecessary skill look beneficial.
- Token reduction claims can be misleading if lower cost comes with hidden success regressions.
- Current `final IR` artifacts are still close to workflow JSON, so artifact-maturity claims should be separated from semantic-IR claims.

## Reporting Requirements

The final report should include:

- system comparison table
- ablation table
- paired delta and regression table
- worst-case setting table
- case studies
- limitations and future work

The report should avoid claiming that Skill IR perfectly compiles all natural-language skills. The current claim is narrower: source-backed skills can be compiled into explicit static semantics and task-local PGO artifacts, then evaluated on held-out tasks across tested models and contexts with regressions visible.
