### 建议说法

>
> Lowering 不只是重新生成一段 Markdown。它把 IR 中的契约渲染成 agent 可读的 `skill.md`，并保留后续 controller、checker 和 adapter 的结构入口。

### 静态三系统实验

| System | Success | Mean score | Hard-gate failed rows | Mean token cost | Mean latency |
|---|---:|---:|---:|---:|---:|
| no-skill | 0/4 | 0.5875 | 1/4 | 6,994.50 | 55,509.25 ms |
| original | 0/4 | 0.4250 | 3/4 | 3,316.00 | 13,122.00 ms |
| ir-static | 0/4 | 0.7000 | 0/4 | 7,821.75 | 31,145.00 ms |

> `ir-static` 比同轮 original 提高 0.275，比 no-skill 提高 0.1125，并把 hard-gate failure 降到 0。但 binary success 仍是 0/4。它稳定完成了保护文件、脱敏、产物生成和 example safety，仍然在 exact classification 和 schema rules 上 0/4。

第一次 calibration 和 static 实验中的 no-skill/original 均值不同，这是模型生成的随机性和批次差异。跨批次数字只作诊断，正式比较使用同一冻结矩阵内的 paired result。

## 31 至 35 分钟：静态与动态如何结合成 Final IR

### 屏幕操作

打开：

```text
docs/skill-ir/env-manager-dual-source-overlay.md
src/benchmarks/skill-ir/repair-evidence.ts
src/benchmarks/skill-ir/dual-source-feedback-run.ts
results/skill-ir/env-manager-dual-overlay-v2-2026-07-16/provenance.json
```

### 建议说法

> 本周真正实现了静态和动态结合，但采用的是 dual-source residual repair，不是把 scorer 金标直接抄回 IR。
>
> `original × development` 只用于确认某种失败在静态编译前就存在；`ir-static × development` 用于判断静态编译后还剩什么 residual。只有 original 和 static 都失败的同源问题才能成为 repair evidence。Original 失败但 static 通过，说明静态 pass 已解决，不再生成 overlay；original 通过但 static 失败，视为静态回归，阻断 Final IR。

### 双源判定表

```text
original fail + static pass -> 已被静态 pass 解决，不进 overlay
original fail + static fail -> reproduced residual，可生成 typed repair
original pass + static fail -> static regression，阻断编译
任何 held-out / scorer expected -> 禁止进入 overlay
```

> Final IR 是 base IR 加通过规则生成的 overlay，再附带 source/base/final digest、development evidence digest、construction identity 和 provenance。`ir-pgo-dev` 只允许 development diagnostic replay；只有 development gate 通过后，`ir-pgo` 才能消费同一产物跑 held-out。

### 双源候选结果

| System / catalog | Success | Mean score | Token cost | 结论 |
|---|---:|---:|---:|---|
| ir-static | 0/4 | 0.7000 | 31,287 | classification、schema 残差 |
| repair v1 | 0/4 | 0.7000 | 58,023 | 没有超过 static，成本更高 |
| repair v2 | 1/4 | 0.6375 | 36,332 | 单行成功，但总体均值和稳定性回归 |

> 两个 Final IR candidate 都没有通过 development gate。v2 虽然出现 1/4 成功，但均分下降，还引入产物缺失和 example safety 回归，所以不能因为出现一个成功样本就晋升。

### 要证明的事情

- 静态与动态结合链路已经实现。
- 动态回流有 gold isolation 和 regression guard。
- Final IR 是候选编译产物，不等于已优化成功。

## 35 至 39 分钟：为什么从 Final IR 转向 executable artifact v1

### 屏幕操作

展开：

```text
benchmarks/skill-ir/pilots/env-manager/packages/executable-artifact-v1/
```

打开：

```text
package-manifest.json
package-provenance.json
validation-policy.json
docs/skill-ir/executable-artifact-runtime.md
```

### 建议说法

> 双源实验暴露出 prompt repair 不够稳定。即使把规则写进 Final IR，模型仍可能不生成文件、生成坏 JSON、改保护文件，或者没有按格式执行。因此下一步不再只加 Markdown 规则，而是把稳定部分固化成 package。

Package v1 的结构是：

```text
skill-ir.json
skill.md
artifacts/contracts/
artifacts/templates/
artifacts/checks/
package-manifest.json
package-provenance.json
validation-policy.json
```

Runner 状态机是：

```text
preflight
  -> template materialization
  -> model generation
  -> validate
  -> at most one sanitized repair
  -> revalidate
  -> stop
  -> offline deterministic scorer
```

> Preflight 校验 package digest、task scope、model/adapter/environment/context、输出路径、workdir containment 和保护文件。Runtime validator 只输出封闭错误码和五个白名单字段：`code`、`relativePath`、`jsonPointer`、`missingField`、`expectedType`。Repair 看不到 scorer expected、secret、绝对路径和自由文本。

### v1 development 结果

| Arm | Success | Mean score | Initial runtime pass | Repair attempts | 结论 |
|---|---:|---:|---:|---:|---|

## 八、老师可能追问的问题和回答

### 8.1 现在到底有没有“skill 优化效果”？

> 有静态 partial correctness 的正向信号：同轮 `ir-static` 相比 original 均分从 0.425 提到 0.70，并消除 hard-gate failure。但 binary success 仍为 0/4，后续 Final IR 和 artifact candidate 都没有通过 development gate。所以当前不能声称完成了稳定优化，只能声称静态 IR 对安全、产物和基础契约有改善，并建立了能发现后续失败的链路。

### 8.2 为什么失败结果也值得汇报？

> 因为每轮失败都把研究问题收紧。Static 说明 prompt 能改善部分规则但 schema/classification 不行；dual-source 说明再加 prompt repair 会回归；artifact v1 说明结构 validator 会 false pass；v2 说明 semantic validator 能触发 repair，但 repair 投影和语义覆盖仍不够。这些结果阻止我们在 held-out 上消耗预算并做错误主张。

### 8.3 静态和动态到底如何结合？

> 静态 source audit 生成 base IR。Original development 结果确认失败 lineage，ir-static development 结果提供静态编译后的 residual。双源规则生成 typed repair，和 base IR 编译成带 provenance 的 Final IR candidate。Held-out 永远不参与生成。当前这条结合链已经实现，但生成的 candidate 没过 development gate。

### 8.4 为什么 dynamic evidence 不直接来自 ir-static？

> 现在是双源。Original 用来证明失败在静态前存在，static 用来定位静态后残差。只看 original 会把已经被 static 解决的问题重复写入 overlay；只看 static 又不知道该失败是原始问题还是静态 pass 引入的回归。

### 8.5 为什么不把 scorer expected 写进 validator？

> 那会造成 gold leakage。Runtime validator 只能用公开 skill、用户可见 task contract 和 agent 可见 workdir。Scorer expected 只在离线评估中存在。V2 还专门做 canary 和 reverse-evidence test，确保去掉公开证据后约束也消失。

### 8.6 为什么先做一个 env-manager，不同时做三个？

> 先隔离基础设施变量。Env-manager 的安全、文件和 schema 契约明确，适合验证 exact source、workdir、scorer、IR、feedback、package 和 repair。三个 skill 同时推进会把 scorer 难度、脚本依赖和方法问题混在一起。下一步需要在第二个真实 skill 上 replication，而不是继续只在 env-manager 上调。

### 8.7 为什么 held-out 没跑？

> 这是预注册合同。Development gate 在付费前冻结为至少 3/4、均分 0.85、无 hard-gate regression、无 infrastructure failure。V2 只有 0/4 和 0.625，所以 held-out 必须阻断。跑 held-out 会污染真正的泛化证据。

### 8.8 为什么不用更多模型把结果跑好？

> 当前实验首先验证单模型纵向机制。Package、scorer 和 repair 尚未成熟时加入模型面板，会把模型差异和基础设施问题混在一起。跨模型主 claim 需要固定 panel、development pooled evidence、per-model 报告和 Wave B replication。现在还不具备这个证据条件。

### 8.9 当前 token 结论是什么？

> 当前没有节省 token 的证据。Original 第一次校准很贵，但 static 和 package 也经常更贵。未来要报告 `compile + profile + N × optimized runtime` 与 `N × original runtime` 的 break-even，同时要求质量不回归。Token 目前是 secondary/future claim。

### 8.10 8.5 MiB parser bundle 是否太大？

> 是已知工程债。它内嵌 TypeScript parser，优点是在临时目录和离线条件下可复现，不依赖 host package install；缺点是 package 很大。将来可以设计 version-bound lightweight ABI，但这会改变 portability 和 integrity contract，必须新 catalog、新 digest、新 lock，不能就地修改冻结 v2。

### 8.11 现在算 L3/L4 artifact 吗？

> 当前是 L3-oriented prototype。它已经有 scripts、checks、schemas、templates、provenance 和 validation notes，但还没通过 development gate，也没有 held-out regression evidence，因此不能叫 validated L3/L4 package。

### 8.12 为什么文档这么多？

> 这周每个设计、实现、lock 和失败实验都单独留痕，优点是可审计，缺点是入口过多。汇报完成后会做一次文档治理：建立权威入口和引用图，把“当前契约”“组件说明”“历史实验”分层，合并重复文档，归档阶段性设计，不直接删除仍被结果和代码引用的文件。

## 九、下周建议计划

## 9.1 第一优先级：文档压缩与入口治理

先做清理，不直接删文件：

1. 枚举 `docs/skill-ir/` 和 `docs/superpowers/` 全部文档。
2. 建立代码、plan、spec、result 对文档的引用图。
3. 将文档标成：`authoritative-current`、`component-current`、`experiment-frozen`、`historical-design`、`superseded`。
4. 建立一个 `docs/skill-ir/README.md` 作为唯一导航入口。
5. 合并重复的 run/design 说明。
6. 历史证据移动到 archive 或在 front matter 标明 superseded，不破坏引用。
7. 更新主 spec/plan，只保留当前状态和明确后续任务。

## 9.2 第二优先级：冻结 v2 失败证据，做 failure audit

不要就地调 v2。先分析：

- Node repair 为什么把 array 修成错误类型。
- 为什么 Vite runtime pass 但 offline classification/schema/example 失败。
- A validator 的 false negative 和 false pass 分别有哪些。
- Repair prompt 五字段是否足以恢复，还是需要 provenance-bound executable patch/template。
- 哪些 schema 规则可从公开 skill 和 AST 推断，哪些必须保持 unconfirmed。

## 9.3 第三优先级：设计新 catalog，而不是修改旧 lock

新设计至少要解决：

- repair 前后都能保留可评分 snapshot，支持真正的 repair attribution；
- schema contract 能表达 public required/format/minLength 等语义；
- classification B 是否进入 production，必须重新设计并评审 gold isolation；
- check-only 与 one-repair 尽量共享 initial generation，减少独立生成噪声；
- package 大小和 parser ABI 的新版本策略。

## 9.4 第四优先级：第二个真实 skill replication

新机制通过 env-manager development 后，选择 `law-to-markdown` 或一个约束清晰的 Wave B skill 做 replication。不得继续只在 env-manager 上证明泛化。

## 十、结束语

建议最后这样总结：

> 这周最大的变化，是项目从合成 skill 和 workflow JSON 为主，推进到了真实 public skill、精确 source provenance、deterministic workdir scorer、静态和动态双源 Final IR，以及可执行 artifact package。静态 IR 已经显示 partial correctness 改善，但所有更强候选都没有通过 development gate，semantic v2 虽然真实触发了 repair，仍然没有修到成功，所以 held-out 被正确阻断。
>
> 目前结果不支持“项目已经把 skill 优化好了”，但支持更具体的研究判断：自然语言规则和 prompt repair 不足以保证稳定执行；provenance-bound executable contract 可以发现更多错误；下一步需要提高 schema/classification 语义覆盖和 repair 可归因性，再在第二个真实 skill 和后续模型面板上验证。
>
> 我希望这次和老师、学长重点讨论三个问题：第一，下一版 semantic catalog 是否应该开始引入受限的 B-layer classification；第二，repair attribution 是否改成共享 initial generation 和 pre/post scorer snapshot；第三，完成文档治理后，第二个 replication skill 选 `law-to-markdown` 还是先选更轻量的中文约束 skill。
