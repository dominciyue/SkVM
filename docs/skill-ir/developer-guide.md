### 1.1 授权 DSL 开发原型

已有接口分为 fixed-context、authoring/material preparation 和当前 inquiry 三组。旧输入与 wire 按版本继续消费；修改某组不意味着可以重新解释旧结果。

| 接口组 | 主要入口 | 需保持的合同 |
|---|---|---|
| 规范声明与义务 | `parseAuthorizationTask`、`compileAuthorizationTask`、`compileAnalysisRequirements` | 只展开作者显式义务与入口；政策期待和源码观察分开；重复、悬空和跨义务引用给出诊断 |
| 渲染与引用 | `renderAuthorizationTask`、`buildAuthorizationSourceCatalog`、`resolveAuthorizationSourceCitation` | 比较臂共享原始事实；模型选择已展示引用，宿主绑定原文件行/文字；字符数不替代 token |
| 模型返回 | versioned wire / compact / policy / outcome result | v1–v6 各按自己的字段和语义验证；不猜缺失答案；错误归一化不交付成功 canonical result |
| 关系与条件 | `compileConditionAnalysisRequest`、`validateRelationCoverage`、`validateConditionAnalysisResult` | 只检查声明/引用/边界关系；`semanticSupport` 保持 unreviewed；条件枚举和实际源码完整性分开 |
| 作者输入与编辑 | `normalizeAuthorizationAuthoringInput`、`composeAuthorizationAuthoring`、`createAuthorizationAuthoringDraft`、`applyAuthorizationLocalEdit` | v1/v2 显式分发；已知元数据可派生，政策、期待与自然语义由作者承担；局部修改限定现有字段 |
| 场景工作区 | `planAuthorizationWorkspace`、`materializeAuthorizationWorkspace`、`compareAuthorizationWorkspaces` | 共同 base 与显式整字段覆盖；保留继承/变化来源；发布限制与示例见[工作区说明](../../examples/authorization-assessment/scenario-workspace/README.md) |
| 源码准备与缺口 | `prepareAuthorizationEvidence`、`discoverAuthorizationEvidence`、`selectEvidenceLocation`、`buildControlContext` | 显式范围、原行号、多片段映射和具名 gaps；词法位置不证明调用语义；ready 只针对已声明依赖 |
| 材料复用 | `reusePreparedMaterial`、`transitionPreparedGaps` | 验证原始源码绑定；保留 pending gaps，具名解释退休理由；旧材料可复用不表示旧答案仍正确 |
| 普通输入/运行 | `loadLocalAuthorizationInput`、`checkLocalAuthorizationInput`、`executeLocalAuthorizationRun`、`inspectLocalAuthorizationOutput` | provider 前核对身份、引用和来源范围；每次 run 建立新 session；未知完成不自动重发 |
| 变化复查 | `createExecutionDependencies`、`compareAuthorizationInput` | 绑定任务、源码、策略、输出合同与实际上下文；只读报告 needs-review，不自动提升答案质量 |
| 语义评价 | `evaluateAuthorizationGeneration*`、各版本 summarize/replay | 使用绑定原答和精确源码的独立评阅；分开语义、证据、传输和交付；旧评分按旧身份复算 |

调用与使用要求：

- 普通方法为 `plain/ledger/conditions`；具体默认和兼容组合由当前解析器与[使用说明](../usage.md)确定。`control-binding-v1`、`explicit-v1`、`current-v1`、领域策略等显式选择，不把旧阶段的推荐当作统一默认。
- 旧 fixed-context `runAuthorizationTask` 使用一次精确源码束、窄模型响应和有界诊断修复；当前 inquiry 使用任务内只读取证，源码预算、调度、局部图及 previous 的详细合同见本文后半部。
- 作者 v2 的编辑器 Schema 为 [authoring-v2.schema.json](../../schemas/authorization/authoring-v2.schema.json)。编辑器负责结构，runtime 继续核对引用、政策和真实源码位置；使用[完整编辑示例](../../examples/authorization-assessment/editor-support/README.md)。
- 普通便携输入通过相对 sourceRoot 与原路径定位源码；`../` 只有在显式输入边界内才可用，symlink/junction 不得悄然改变来源范围。片段省略处没有引用权限。
- `provider-unavailable` 且零 dispatch 可在修正路由后建立新 session；已经派发但无终态的请求按未知完成保留。使用自定义本地路由时明确 `SKVM_CACHE`，不要把环境路径问题归为方法失败。
- Token 归一化由 `src/measurement/token-accounting.ts` 负责。[计量工具](../../scripts/token-accounting/README.md)区分非缓存 input、含缓存 input 与 unknown；实际 USD 缺报时不由字符数或估价代填。

从仓库根检查普通输入：

```powershell
bun ./src/index.ts authorization check --input=./examples/authorization-assessment/assessment.json
```

真实运行、修改和 inspect/compare 按[使用说明](../usage.md)以及[任务语义示例](../../examples/authorization-assessment/task-semantics/README.md)、[证据编辑示例](../../examples/authorization-assessment/evidence-editing/README.md)、[原 skill 使用包](../../examples/authorization-assessment/reusable-skill/SKILL.md)操作。`run` 会调用配置的模型；check/inspect/compare 是离线检查。

历史复现从[实验目录](../../results/skill-ir/experiment-catalog.json)进入对应结果根及当时任务书，再选择已有 `replay`/`evaluate` 命令。旧 runner 如果因冻结实现变化而拒绝，保留拒绝并回到其提交，不改旧摘要来放行。先前指南中的逐阶段测试数、付费运行命令和重复结果可从治理前 Git 提交 `23f0f976` 恢复；不再作为日常启动清单。

## 2. 当前端到端流程

### 2.1 收集真实 trace

普通使用从一次自然任务开始，由 bare-agent 自动收集本次运行记录：

```powershell
skvm run --prompt="<task>" --skill=./skill --workdir=./project --model=<id> --optimize
```

优化模型默认沿用 `--model`，需要区分时指定 `--optimizer-model`。已有日志时，保留原 skill、成功/失败记录、失败 sidecar、模型身份与任务上下文，使用高级日志入口。该入口不会重跑原任务：

```powershell
skvm jit-optimize `
  --skill=path/to/skill-dir `
  --task-source=log `
  --logs=path/to/log1.jsonl,path/to/log2.jsonl `
  --failures=path/to/log1-failure.json,path/to/log2-failure.json `
  --optimizer-model=<id> `
  --target-model=<id>
```

### 2.2 审阅 proposal

```powershell
skvm proposals list
skvm proposals show <id>
skvm proposals accept <id>
```

接受 proposal 会应用选定改动，但不是质量认证。检查 Evidence 中的未知项和剩余职责；研究效果仍需相应的比较证据。

### 2.3 生成并消费新包

自动入口会尝试导出新包；高级日志入口可用 `--package-out=<new-empty-directory>` 指定位置。API request/pytest、Env preset 和外部 skill import 按任务需要使用。查看包内 `OPTIMIZATION-USAGE.md` 了解入口和限制；新包应当：

- 可独立定位与加载；
- 记录 source、proposal、选中版本、已有接受决定和产物摘要；
- 保留未固化的说明与 agent 职责；
- 在新消费任务中记录真实 trace；
- 由与公开合同一致的 checker 或明确人工接受边界验证。

## 4. 实现纪律

- 先写失败测试，再做最小实现，最后运行聚焦测试与必要的更广验证。
- 通用 core 不按 skill id、case id 或模型名分支。
- 研究 gate 只保护冻结输入、外部副作用、付费执行、held-out 和主张资格；本地可逆修改不重复加门。
- scorer/checker 必须与公开接口一致，不得私下要求未公开字段或答案。
- 保留完整分母、失败行、未知成本与 stop-loss；不得为了漂亮结果补跑或换样。
- 结果写到 `results/skill-ir/`，文档链接结果，不复制长流水。

## 6. 常见失败处理

- 输入摘要不匹配：停止，确认拿到的是否为冻结版本，不覆盖原件。
- checker 拒绝但公开合同满足：按测量身份问题处理，不把它解释成模型失败。
- 基础设施失败：保留失败行与调用成本，按任务书 stop-loss 收口。
- 新包遗漏职责：退回固化边界，不能用说明文档删除原职责。
- 文档链接失败：迁移普通导航；若目标是运行时按摘要读取的版本化材料，保留原路径与原字节。

## 8. 授权运行组件参考

### Authorization authoring and input applicability

The ordinary agent loop now stops before dispatching beyond `maxIterations`, including unscoped source runs. A tool-bearing last response is retained with its executed tools and counted tokens, but missing continuation returns an iteration-budget error instead of `ok`. A final response received within the limit still succeeds. The former `stopBeforeIterationLimit` option remains accepted for compatibility; the boundary applies universally. A retained failed source trace may still inform optimization, but capture readiness and optimizer completion do not establish task delivery.

Ordinary full-skill runs select the current strategy with `skvm run --prompt=<task> --skill=<original-SKILL.md> --model=<provider/model> --adapter=bare-agent --authorization-scope=<input.json> --authorization-domain-tools --authorization-strategy=guided-evidence-v2 --authorization-trace=<trace.json>`. The strategy enum comes from the shared runtime schema; both CLI validation and adapter setup reject non-legacy strategies without domain tools before creating a provider. A supplied inquiry declaration compiles on the host; a natural brief still requires counted authoring. This entry does not optimize/export a skill: that remains the separate ordinary `--optimize` pipeline.

Local explanation work remains eligible after its first interpretation while its question is still awaiting verification. Fresh interpretation and binding duties precede revisiting verification duties; checked/closed work is excluded. A successful same-question item clears an earlier local routing/container rejection, but not a concrete rejected target, another question's rejection or source invalidation. Raw failed proposals remain archived. Corrections replace existing target keys; creating renamed keys does not withdraw earlier rules. For ordinary explicit replacements, an omitted model reason is recorded as `host:explicit-local-replacement` with before/after versions rather than rejected; dependency relevance reasons remain required. This provenance label supplies no semantic justification. Memos lifecycle replay exercises the actual first accepted proposal and its next rejected update; it removes the stale-envelope failure while retaining three newly exposed schema errors, without claiming a checked graph or semantic correctness.

`inquiry-local-extraction.ts` owns the shared local update item schemas and the narrower `localExtractions` contract. Each offered task carries one current WorkItem, the current question/premises, required caller window IDs, existing target keys and independent policy. Whole original numbered windows appear once in `sourceWindows`; older evidence remains a metadata catalog. The model omits question and evidence fields from extraction items. The runtime binds them to this offered task, retains raw/expanded proposals, and delegates the same per-item or atomic validation to `applyControlUpdates`. Invalid siblings cannot overwrite host scope or erase good work. An actual source change invalidates the offered task. Meaning, prose-to-predicate alignment and user/policy mapping remain unreviewed; the host does not derive them from symbol equality.

Guided inquiry and native dispatch merge explanation into the next ordinary provider call. Explicitly rerequested old ranges become current again even when their stable evidence ID is reused. Current model diagnostics are deduplicated and bounded to sixteen; the complete failures and original responses stay in reports. Source display accounting requires the actual host-rendered window object to match ID, repository/ref, path, digest, bounds and text. Equal text in another path or a catalog ID cannot establish shown evidence; never-shown source cannot satisfy citations. Native source tool history carries metadata while the current context provides selected raw windows. Tests exercise both entry points, two-call entry/helper explanation, atomic and partial rejection, explicit null versus unknown, invalidation, reused ranges, false aliases and actual selected display bytes. Real source-quality probes and measured progress remain required separately.

For native `guided-evidence-v2` with a complete supplied `input.inquiry`, the host compiles that declaration during runtime initialization and starts the same worklist before the first provider request. It does not expose a redundant authorization_compile tool. `compilationOrigin:host-input` and `compilationToolCalls:0` distinguish this computation from a model-authored declaration; no source behavior is filled in. A natural brief still exposes the compile tool, counts every admitted compilation attempt in the exploration budget and reports model-tool origin after success. Original skill injection and companion reads use the existing loader and reference tool; legacy/domain-evidence-v1 remain on their existing compilation flow. Tests cover automatic first source explanation, checked delivery with one read plus one check, retained companion tools and counted natural authoring.

The first real Paperless entry interpretation exposed a paraphrased unknown premise plus a requested atomic transaction: the exact-span validator rejected the premise and correctly rolled back the group. The shared explanation guide now states that unspecified entries can be omitted, submitted spans remain verbatim, and per-item updates are the default. It illustrates rejection and effect reachability on generic distinct paths, explicit binding predecessors, and remaining called controls before closure. These are model instructions rather than automatic semantic validation. The original proposal and subsequent network failure remain separate; the matched real-task recheck must establish any improvement.

`inquiry-worklist.ts` expands the six compiled duties before any control proposal. Original indexed symbol hints locate an entry; a unique complete entry receives a bounded original read, then an interpretation duty. Lexical references are discovered only within that selected definition's actual line bounds, even when a wider overlapping range was read. They are deduplicated by question, original candidate and symbol. An unclassified reference remains an optional lead with `reference-relevance-unconfirmed` until a related explicit dependency or displayed candidate selection requests its read. Unique spelling does not establish receiver identity or relevance. Ambiguity accepts explicit `workSelections:[{questionId,itemId,candidateId}]`; the host checks question ownership. A same-question accepted source-bound entry rule may also anchor a unique indexed declaration when its cited original window includes the declaration line and matches path/digest. `selectedBy` records `explicit-selection`, `unique-index-candidate` or `accepted-entry-citation`. Explicit selection wins; non-entry or other-question rules, unread evidence and multiple matching declarations cannot resolve ambiguity. Citation-based location is recomputed from the current slice, and source invalidation still blocks it. This location association adds no semantic rule or helper relevance. Related duties follow the actual entry window without inventing optional roles. Reads reuse exact digest/range coverage, alternate questions, and share at most two automatic actions until `beginStep()`.
